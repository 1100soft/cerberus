Resolve the detected CI failure without confusing a tag, execution worktree, source branch or integration destination.

Verify the GitHub workflow run, run attempt, exact failed SHA, ref name and whether it is a branch or a tag. Fetch the exact commit if necessary, without moving local branches. Inspect failed-job logs first and classify the failure. For a source-code correction, reproduce at the failed commit in an isolated worktree; never modify the original worktree or substitute a clone.

Before making a correction, establish the authorized integration target and distinguish ordinary branch failures from release/tag failures:
- Ordinary persistent branch: the verified failed workflow's actual refs/heads/<branch> is sufficient authorization to correct that same branch when its configured publication remote and merge ref match the verified repository/remote branch. An absent cerberus.ciTarget or AGENTS.md policy is NOT a blocker for this case. Record the workflow, failed SHA, configured upstream, remote URL and current target tip as evidence. Never infer the target from the execution worktree's checkout. A newer target tip is normal: reproduce the exact failed SHA, retain the observed target tip, and let Review/Integrate verify/reconcile advancement without overwriting it.
- Explicit repository-local cerberus.ciTarget or tracked AGENTS.md development policy takes precedence when applicable. Verify it against the remote and workflow; conflicting explicit policies or an upstream pointing to a different branch/repository are BLOCKED, not reasons to guess.
- Tag/release failure: the tag is immutable context, never an integration branch. Require explicit cerberus.ciTarget or a tracked AGENTS.md development policy. Do not infer a target from main, the default branch, origin/HEAD, a containing branch or ancestry. Missing authorization is BLOCKED with the exact missing setting/policy named.
- Temporary correction/* or automation-owned execution branch: require its verified existing integration contract or explicit development-target policy. Do not make correction chains targeting disposable branches.

Classify the failure before creating correction resources. Hosted-runner capacity/network outages require a bounded retry of failed jobs when warranted and an honest pending/unverified report, not a source commit or correction worktree. Missing repository variables, secrets, signing credentials or provider permissions require a precise configuration report; check exact expected variable names against configured names without exposing secret values. Never fabricate Store/signing identities, weaken a release guard or invent a commit to satisfy the chain. An app/runtime failure (including unsupported conversation resume) is distinct from a failed CI job; preserve the original context and report that a fresh run/context recovery is required rather than repeatedly resuming an unsupported conversation.

For an ordinary branch failure, base the correction on the exact failed commit. For an immutable release/tag failure, reproduce there but make the minimal correction on the verified development target; do not merge release-only history into development. If a release tag disagrees with application metadata, do not weaken the version guard or suppress real release CI. Preserve published tags; report that a corrected, separately authorized release will be needed. A source-provenance tag is not a release and should not enter package CI; verify that distinction before proposing a trigger change.
